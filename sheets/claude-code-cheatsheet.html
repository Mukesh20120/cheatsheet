Claude Code

The exact syntax for CLAUDE.md, permissions, subagents, skills, hooks, MCP and sandboxing — plus what silently breaks in each.

← 1 ~/.claude/settings.json  (user scope, applies to all projects)
← 2 {
  "model": "claude-opus-4-8",
← 3  "permissions": {
    "allow": ["Bash(git *)", "Edit"],
    "deny":  ["Bash(rm -rf *)", "WebFetch"]
  },
← 4  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{ "type": "command", "command": "npx prettier --write ." }]
    }]
  },
← 5  "env": { "CLAUDE_CODE_MAX_OUTPUT_TOKENS": "8192" }
}

What each part does

  1. 1. Config resolves in layers: enterprise policy → ~/.claude/settings.json (user) → .claude/settings.json (project, committed) → .claude/settings.local.json (project, gitignored). Later layers override earlier ones.
  2. 2. model pins the default model for every session started here — overridable per-run with --model or mid-session with /model.
  3. 3. permissions.allow/deny are glob-style rules checked before every tool call. This is the actual access-control layer — not the interactive y/n prompts, which are just the fallback for anything unmatched.
  4. 4. hooks run shell commands at lifecycle events. This one reformats every file Claude edits or writes, automatically, with no prompt.
  5. 5. Plain env vars Claude Code itself reads (context budget, telemetry, proxy settings) — separate from your project's own .env.

Install & First Run

01 / getting on the machine

Install (npm)

Global install, needs Node 18+.

npm install -g @anthropic-ai/claude-code

Install (native, no Node)

Standalone binary — skips the Node/npm dependency chain entirely.

curl -fsSL https://claude.ai/install.sh | bash
TipPrefer this on CI runners and fresh VPS boxes — one less thing (Node version drift) to debug at 2am.

Launch & Auth

Run inside the project directory you want it working on.

cd my-project && claude

First run opens a browser to authenticate against your Claude.ai or Console account.

Update

Claude Code updates itself; force it explicitly when a fix is announced.

claude update

Version & Doctor

Sanity-check the install before filing a bug.

claude --version
claude doctor

.gitignore essentials

Local overrides and session state should never hit the repo.

.claude/settings.local.json
.claude/shell-snapshots/
.mcp.local.json
Gotcha.claude/settings.json (no .local) is meant to be committed and shared with the team — don't gitignore that one by mistake, it's your project's shared permission and hook config.

CLI Basics & Modes

02 / how you actually invoke it

Interactive mode

Default — a REPL you type into, holds context across turns.

claude

Print mode (one-shot)

Non-interactive — runs a single prompt to completion and exits. What you use in scripts.

claude -p "summarize the diff on this branch"

Pipe input in

Stdin becomes part of the prompt context — logs, diffs, test output.

git diff | claude -p "review this diff for bugs"

Continue / resume a session

--continue picks up the most recent conversation in this directory; --resume lets you pick which one.

claude --continue
claude --resume
Gotcha--continue is scoped to the current working directory. Run it from a different folder and it silently starts nothing — it won't cross-load a session from elsewhere.

Pick a model for this run

Overrides settings.json for a single invocation only.

claude --model claude-opus-4-8

Flags worth memorizing

FlagDoes
-p, --printRun once, non-interactively, then exit
--continueResume the last session in this cwd
--resumePick a past session from a list
--modelOverride the model for this run
--allowedToolsWhitelist tools for this run only
--permission-modeplan / acceptEdits / bypassPermissions
--output-format jsonMachine-readable output for scripting
--dangerously-skip-permissionsNo prompts, no allow/deny checks at all

Terminal integration quirks

Behavior differs slightly by terminal emulator.

GotchaIn some terminals (older Windows Terminal builds, tmux without proper passthrough) box-drawing and the live diff view render as garbled characters — switch to a modern terminal (iTerm2, Ghostty, VS Code's integrated terminal) rather than debugging your prompt.

Sessions & Context

03 / managing the window

/clear — wipe context

Starts a brand-new context; nothing from before persists.

> /clear

/compact — summarize & continue

Replaces history with a summary but keeps the thread going — use this, not /clear, when you still need the thread of a long task.

> /compact
> /compact "keep the auth bug details, drop the CSS discussion"

Auto-compact

Claude Code compacts automatically as you approach the context limit.

GotchaAuto-compact runs on a token buffer, not a hard wall — it can trigger mid-task on a big file read. If a compaction happens right before a critical edit, re-state the constraint explicitly afterward; summaries lose specificity, not just word count.

/context — inspect usage

Shows a breakdown of what's actually consuming your context window.

> /context

/cost — check token spend

Running total for the current session.

> /cost

When to actually start a new session

Not every task warrants /clear — but some symptoms mean you should stop patching and restart.

SymptomAction
Task genuinely finished/clear, start fresh
Switching to an unrelated file/feature/clear
Same task, conversation just long/compact
Claude re-suggesting something already rejected/clear — stale context is steering it wrong
Repeated wrong edits to the same fileNew session; re-state the goal fresh rather than correcting in place

CLAUDE.md & Project Memory

04 / durable instructions

Generate one

Scans the repo and drafts a CLAUDE.md from what it finds — always review it, don't trust it blind.

> /init

Where CLAUDE.md files live

PathScope
./CLAUDE.mdProject root — committed, shared with the team
./CLAUDE.local.mdProject root — personal, gitignored
~/.claude/CLAUDE.mdYour user-level defaults, every project
packages/api/CLAUDE.mdLoaded only when Claude is working inside that subfolder — great for monorepos

What actually belongs in it

Terse, imperative, project-specific. Not documentation.

## Commands
bun run dev      # start dev server
bun test          # run unit tests
bun run lint --fix

## Conventions
- Use server actions, not API routes, for mutations.
- Tailwind only — no CSS modules.
TipTreat it like onboarding notes for a new hire, not a README. If a human wouldn't need to be told, Claude doesn't either.

Import other files

Keep CLAUDE.md short by pulling in detail on demand.

See @docs/api-conventions.md for endpoint patterns.

CLAUDE.md vs. auto-generated memory

CLAUDE.mdAuto/session memory
Who writes itYou, by handClaude, inferred from the conversation
PersistenceAlways loaded, every sessionModel-managed, can be edited/forgotten
Best forStable facts: commands, conventions, architectureThings learned mid-task you haven't codified yet
Trust levelHigh — you control itVerify before relying on it for anything critical
GotchaDon't rely on auto memory to remember a hard constraint ("never touch the payments module") across sessions — write it into CLAUDE.md. Auto memory is a convenience layer, not a substitute for explicit instructions.

Plan Mode & Editing Workflow

05 / think before it writes

Enter plan mode

Claude reads and reasons but makes no edits until you approve a plan.

Shift+Tab (cycles through modes)
> /plan "add rate limiting to the login endpoint"

Approve and execute

Once the plan looks right, accept it — Claude then implements exactly that plan.

TipFor anything touching auth, payments, migrations, or deletes — always route through plan mode first. The cost of reading a plan is a minute; the cost of an unreviewed multi-file edit going sideways is your afternoon.

Editing modes compared

ModeBehavior
defaultPrompts before every file edit and non-read-only command
planRead-only — proposes a plan, makes zero edits until approved
acceptEditsAuto-approves file edits; still prompts for shell commands outside allow-list
bypassPermissionsNo prompts at all, for anything — see danger note below

Undo an edit / rewind

Claude Code keeps checkpoints you can roll back to independent of git.

Esc Esc (rewind to a previous checkpoint)
GotchaCheckpoints cover files Claude touched in-session — they are not a replacement for git. Commit real checkpoints yourself; don't treat rewind as your only safety net for a long unstaged session.

Permissions

06 / what it's allowed to touch

Inspect current rules

> /permissions

Allow/deny syntax

Tool-name plus an optional glob-matched argument pattern.

{
  "permissions": {
    "allow": ["Bash(npm run test:*)", "Edit(src/**)"],
    "deny":  ["Bash(git push --force*)", "Read(.env*)"]
  }
}

One-time vs persistent grants

When prompted, you can allow just this call, or allow this pattern for the rest of the session/project.

Tip"Allow for this project" writes the rule into .claude/settings.local.json automatically — check that file periodically, it accumulates grants you forgot you gave.

Restrict tools for one command

Useful for a script that should only ever read, never write.

claude -p "audit this repo for secrets" --allowedTools Read Grep

--dangerously-skip-permissions

Disables every permission check — every edit, every shell command, no prompts, no allow/deny list consulted.

claude --dangerously-skip-permissions
DangerThis is the flag that lets Claude Code rm -rf or force-push without asking. Only ever pair it with a sandbox (Docker/native) that has no access to anything you'd mind losing — never run it directly against your real filesystem or a machine with prod credentials.

Enterprise-managed policy

Org admins can pin rules that individual settings files cannot override.

# /Library/Application Support/ClaudeCode/managed-settings.json
{ "permissions": { "deny": ["Bash(curl *)"] } }

Sandboxing

07 / containing the blast radius

Docker sandbox pattern

Mount only the project, run bypass mode inside, throw the container away when done.

docker run -it --rm \
  -v $(pwd):/workspace -w /workspace \
  node:22-slim bash -c \
  "npm i -g @anthropic-ai/claude-code && claude --dangerously-skip-permissions"
TipThis is the standard pairing for autonomous / unattended runs (Ralph-loop style): full permission bypass is fine because the container itself is the safety boundary, not the flag.

Native sandbox mode

OS-level isolation (filesystem + network) without needing Docker at all.

{ "sandbox": { "enabled": true, "network": "none" } }
GotchaNative sandboxing is OS-dependent (seatbelt on macOS, namespaces on Linux) — it isn't identical across platforms. Don't assume a config that isolates network access on one OS behaves the same on another; verify per-platform.

Docker vs. native sandbox — which one?

DockerNative
Setup costNeeds Docker installed & runningNone — built into Claude Code
Isolation strengthFull container boundaryOS-level, lighter-weight
Best forUnattended/autonomous loops, CIQuick "let it run without asking" on your own machine
PortabilityIdentical everywhereBehavior varies by OS

Slash & Custom Commands

08 / built-in and your own

Built-in commands worth knowing

CommandDoes
/initGenerate a CLAUDE.md from the repo
/clearWipe context, fresh start
/compactSummarize context, keep going
/modelSwitch model mid-session
/permissionsView/edit tool permission rules
/agentsList/manage available subagents
/hooksView configured hooks
/mcpList connected MCP servers & auth status
/reviewRun a structured code review on current changes
/cost, /contextSpend and context-window introspection

Custom command — the file

Any markdown file in .claude/commands/ becomes a slash command named after the file.

# .claude/commands/review.md
---
description: Review a PR diff for security issues
allowed-tools: [Bash(git diff:*), Grep]
---
Review this diff for SQL injection, auth bypass,
and secrets. Diff: !`git diff main`

Invoke it

> /review

Arguments

$ARGUMENTS captures whatever follows the command name.

# .claude/commands/fix-issue.md
Find and fix issue #$ARGUMENTS from the tracker.
> /fix-issue 412

Inline shell in a command

A backtick-prefixed ! line runs the shell command and splices its output into the prompt.

Current branch: !`git branch --show-current`
GotchaInline shell execution in commands still respects your permission rules — if Bash(git *) isn't allow-listed, the command will stall on a prompt the first time it runs, even though you wrote the command yourself.

Personal vs project commands

.claude/commands/ is per-project; ~/.claude/commands/ is available in every project you open.

Subagents

09 / parallel, isolated workers

Define one

A markdown file with frontmatter in .claude/agents/.

# .claude/agents/docs-explorer.md
---
name: docs-explorer
description: Looks up library docs and API references. Use proactively whenever unfamiliar library usage comes up.
tools: [WebFetch, Grep]
---
You research library documentation and report back
concise, accurate usage examples. Never write code
yourself — only report findings.

Invoke explicitly

> Use the docs-explorer agent to check BetterAuth's session config

Automatic delegation

The main agent decides on its own to delegate when a subagent's description matches the task.

TipWrite the description field like a job posting, not a summary — it's the only thing the router reads to decide whether to hand off work. Vague descriptions get skipped in favor of the main agent just doing it inline.

List & manage

> /agents

Isolated context — the whole point

A subagent's conversation doesn't pollute the main session's context window.

GotchaIsolation cuts both ways: the subagent doesn't see what the main thread already tried, so it can re-discover (or re-break) something the main agent already fixed. Give subagents just enough context in the prompt to avoid redoing work.

Agent Skills

10 / packaged, reusable expertise

Skill folder layout

.claude/skills/
  react-components/
    SKILL.md
    examples/button.tsx

SKILL.md frontmatter

The description is what gets matched against the task — this is the entire trigger mechanism.

---
name: react-components
description: Best practices for building accessible React components with this project's design system. Use when creating or editing any .tsx component.
---
## Conventions
- Functional components only, no class components.
- Import UI primitives from `@/components/ui`.

Personal vs project skills

~/.claude/skills/ loads in every project; .claude/skills/ is project-scoped and can be committed for the team.

Use as a slash command

A skill can also be invoked directly instead of waiting for auto-discovery.

> /react-components build a dropdown menu

Skills vs. Subagents vs. Hooks — the confusion triangle

SkillSubagentHook
What it isInjected knowledge/best-practicesA separate agent with its own contextA shell command triggered by an event
Runs inMain conversation, on-demandIts own isolated conversationOutside the model entirely
Good for"How we do X here"Parallel research/explorationDeterministic side-effects (lint, format, notify)
Triggered byDescription match to the taskExplicit ask or auto-delegationTool-use lifecycle events
GotchaIf Claude keeps ignoring a skill you wrote, the problem is almost always the description line, not the content below it — that line is doing 90% of the triggering work, so write it like a search query someone would type, not a title.

Hooks

11 / deterministic side effects

Lifecycle events

EventFires
PreToolUseBefore a tool call — can block it
PostToolUseAfter a tool call succeeds
UserPromptSubmitWhen you submit a prompt, before the model sees it
StopWhen the agent finishes responding
SessionStart / SessionEndSession lifecycle boundaries

Auto-format after every edit

{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{ "type": "command",
        "command": "npx prettier --write \"$CLAUDE_FILE_PATH\"" }]
    }]
  }
}

Block a dangerous command

A PreToolUse hook that exits non-zero stops the tool call before it runs.

#!/bin/bash
# .claude/hooks/block-force-push.sh
if [[ "$CLAUDE_TOOL_INPUT" == *"push --force"* ]]; then
  echo "blocked: force push" >&2
  exit 2
fi

Exit code semantics

0Allow, output ignored
2Block the action, stderr shown to the model
otherNon-blocking error, logged
GotchaPeople assume any non-zero exit blocks the tool call. Only exit code 2 does. A hook script that fails with 1 because of a typo will silently let the original action through — test hooks by deliberately triggering them, don't just trust the config.

Inspect configured hooks

> /hooks

MCP Servers

12 / plugging in outside tools

Add a server

claude mcp add context7 \
  --transport http https://mcp.context7.com/mcp

Project-scoped config file

Checked into the repo so the whole team gets the same servers.

# .mcp.json
{
  "mcpServers": {
    "context7": { "type": "http", "url": "https://mcp.context7.com/mcp" },
    "github": { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-github"] }
  }
}

Scope levels

ScopeStored inVisible to
local~/.claude.json (per-project entry)Just you, just this project
project.mcp.json (committed)Whole team, this repo
user~/.claude/settings.jsonJust you, every project

Check connection & auth status

> /mcp

Grant tool access per server

MCP tools go through the same permission system as built-in tools, namespaced by server.

{ "permissions": { "allow": ["mcp__github__create_issue"] } }
GotchaA committed .mcp.json with an OAuth server prompts every teammate to authenticate on their own machine the first time — that's expected, not a broken config. Don't put personal tokens in the committed file; use .mcp.local.json or env-var substitution for secrets.

Beyond the Local CLI

13 / desktop, web, remote, scheduled

Claude Code on the web

Sessions run in the cloud against a connected GitHub repo — no local machine needed. Good for kicking off work from anywhere and reviewing via a PR.

Desktop app — multiple sessions

Run several sessions in parallel, each on its own git worktree, with live diff and plan views per session.

Dispatch from mobile

Pair the mobile app with a desktop machine; tasks sent from mobile land on that paired desktop.

GotchaMobile dispatch needs an explicit path hint to know which project you mean — "fix the bug" with no path just stalls or picks the wrong repo if you have several open.

Scheduled tasks

Recurring runs (daily summary, nightly test sweep) configured via desktop app or CLI, tied to a project and a permission mode.

claude schedule create \
  --project ~/code/api-server \
  --cron "0 8 * * *" \
  --prompt "summarize yesterday's merged PRs into summary.md"

Remote control from CLI

Attaches a running session to a project so it can be continued and monitored from another device.

Chat-platform channels (e.g. Telegram)

An official plugin lets you drive Claude Code from a chat app via a bot token — same permission model applies underneath.

It's not only for code

The same agent loop drives spreadsheet, slide, and browser-automation tasks — "Code" is the product name, not a scope limit.

Last-Minute Recall

14 / five minutes before you need it

Reflexes

  • Stuck plan mode? Shift+Tab cycles modes.
  • Long task drifting? /compact, not /clear.
  • Switching feature entirely? /clear, not /compact.
  • About to touch auth/payments/migrations? Force plan mode first.
  • Bypass flag anywhere? Confirm you're inside a sandbox first.
  • Subagent not triggering? Rewrite its description, not its prompt body.
  • Hook silently not blocking? Check it exits with code 2 exactly.
  • Team not getting your MCP server? Check it's in .mcp.json, not local scope.
  • Committed the wrong settings file? settings.local.json is the one to gitignore.
  • Session forgot a hard rule? Put it in CLAUDE.md, not just the chat.

Syntax traps

  • Permission rules are glob patterns, not regex — Bash(git *) works, Bash(git .*) doesn't.
  • $ARGUMENTS in commands is one blob, not positional args — split it yourself if you need $1/$2 behavior.
  • Skill/subagent description fields are matched, everything else is just payload.
  • Inline !`cmd` shell in commands still needs permission allow-listing.

Limits & costs worth knowing

  • Context window is finite per session — auto-compact fires on a token buffer, not a fixed message count.
  • /cost reports the running spend for the current session only, not lifetime usage.
  • Scheduled/background tasks still consume the same usage quota as interactive sessions.
  • Native sandbox isolation guarantees differ by OS — verify, don't assume parity.
