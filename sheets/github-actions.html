The whole model, in one file
# .github/workflows/ci.yml  — filename is free, folder is not
name: CI                       ← 1

on:                             ← 2
  push:
    branches: [main]
  workflow_dispatch:

env:                            ← 3
  NODE_ENV: test

jobs:                           ← 4
  test:
    runs-on: ubuntu-latest       ← 5
    steps:                      ← 6
      - uses: actions/checkout@v4   ← 7
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - name: Install & test
        run: |                  ← 8
          npm ci
          npm test

  deploy:
    needs: test                  ← 9
    if: github.ref == 'refs/heads/main'  ← 10
    runs-on: ubuntu-latest
    steps:
      - run: echo "shipping"

Read it once

  1. name — what shows in the Actions tab. Optional.
  2. on — the trigger. Without it the workflow never runs.
  3. env — variables for everything below. Also valid on a job or a step.
  4. jobs — top-level map. Keys are job IDs you reference elsewhere.
  5. runs-on — the runner VM. Fresh machine per job.
  6. steps — ordered list, shared filesystem, same runner.
  7. uses — run someone else's action.
  8. run — run a shell command. | for multi-line.
  9. needs — turns parallel into sequential.
  10. if — condition on a job or a step.

Git recall

the layer underneath

Local loop

git initstart tracking this folder (creates .git)
git statuswhat's changed / staged
git add .stage everything
git commit -m "…"snapshot the staged files
git log --onelinehistory + commit hashes
git checkout <hash>move HEAD to an old snapshot

Undoing

git revert <hash> — creates a new commit that reverses that one. History intact. Safe on shared branches.

git reset --hard <hash> — deletes commits after that point. Rewrites history.

RuleRevert on anything pushed. Reset only on local, unshared work.

Branches

git branchlist branches
git checkout -b featcreate + switch in one go
git merge featmerge feat into current branch
git branch -d featdelete after merging

A branch is just a movable pointer to a commit. Merge conflicts are resolved by hand, then committed.

Remote

git remote add origin <url>link local → GitHub
git push -u origin mainpush + set upstream (first time)
git pullfetch + merge remote changes
git clone <url>copy a repo, origin set automatically
AuthPassword auth is dead — push with a Personal Access Token. To edit workflow files the PAT needs the workflow scope.

Collaborating

  • Collaborator — direct push access, granted by the owner.
  • Fork — your own copy; the route for outsiders.
  • Pull request — propose a merge, get review, then merge.
  • Issue — discuss before writing code; link it from the PR.

Standard flow: fork → clone → branch → commit → push → open PR against upstream.

node_modules/

Keeps junk and secrets out of history. Add it before the first commit — ignoring a file later doesn't untrack it.

Events

what starts a run

The ones you'll use

pushcommits land on a branch
pull_requestPR opened / updated / closed…
workflow_dispatchmanual button in the UI
schedulecron
issuesissue opened, labeled, closed…
workflow_callcalled by another workflow
repository_dispatchexternal API trigger

Multiple triggers

on: [push, workflow_dispatch]

# or the expanded form when you need filters
on:
  push:
    branches: [main]
  workflow_dispatch:

Any one of them firing starts the workflow.

Scheduled runs

on:
  schedule:
    - cron: '0 3 * * 1'   # Mon 03:00 UTC

Fields: minute, hour, day-of-month, month, day-of-week.

NoteAlways UTC, only on the default branch, and GitHub may delay it under load.

Manual input

on:
  workflow_dispatch:
    inputs:
      target:
        description: Where to deploy
        required: true
        default: staging
        type: choice
        options: [staging, production]

Read it with ${{ inputs.target }}.

Activity types & filters

narrowing the trigger

Activity types — which flavour

on:
  pull_request:
    types: [opened, reopened, closed]
  issues:
    types: [opened, labeled]

Default for pull_request is opened, reopened, synchronize. Declaring types replaces that default entirely.

Branch & tag filters

on:
  push:
    branches:
      - main
      - 'dev-*'        # dev-x, no slashes
      - 'feat/**'      # feat/a/b, slashes ok
    branches-ignore: ['exp/**']
    tags: ['v*']
GotchaYou cannot use branches and branches-ignore on the same event. Pick one.

Path filters

on:
  push:
    paths: ['src/**']
    # or skip runs for doc-only commits
    paths-ignore: ['**.md', 'docs/**']

Saves minutes on commits that can't break the build.

push vs pull_request

push on a branch with an open PR fires on every commit — filters apply to the branch you pushed to.

pull_request filters apply to the target branch (where it's merging to), not the source.

Typical setupRun tests on pull_request, run deploy on push: branches: [main].

Forked PRs

  • A first-time contributor's PR needs manual approval before workflows run.
  • Fork PRs get a read-only GITHUB_TOKEN.
  • Secrets are not exposed to fork PRs.

That's deliberate — otherwise anyone could open a PR that prints your secrets.

Cancel & skip

Cancel a live run from the Actions tab → run → Cancel workflow.

Skip a run entirely with a commit message flag:

git commit -m "fix typo [skip ci]"

Also accepted: [ci skip], [skip actions], [no ci]. Works for push and pull_request.

Jobs & steps

the execution units

Hierarchy

Workflow → many jobs → many steps.

  • Jobs run in parallel by default, each on its own fresh runner.
  • Steps run in order on one runner, sharing the filesystem.
  • A failing step fails the job; a failing job fails the workflow.
ConsequenceNothing on disk survives between jobs. Passing data between them needs artifacts or outputs.

Runners

runs-on: ubuntu-latest   # windows-latest, macos-latest

Pre-installed on ubuntu: Node, Python, Git, Docker, the AWS CLI and much more. Public repos: free minutes. Private repos: billed, and macOS costs ~10× Linux.

Self-hosted runners: runs-on: self-hosted.

run vs uses

# uses — someone else's packaged code
- uses: actions/checkout@v4
  with:
    fetch-depth: 0

# run — a shell command on the runner
- name: Install
  run: npm ci

# run — multiline block
- run: |
    npm run build
    ls -la dist

One step is either run or uses. Never both.

Sequencing with needs

jobs:
  lint:    { runs-on: ubuntu-latest, … }
  test:    { runs-on: ubuntu-latest, … }
  deploy:
    needs: [lint, test]     # waits for both

needs builds the dependency graph. If a needed job fails, dependants are skipped — that's how you stop a broken build from deploying.

Reading a failed run

  • Actions tab → run → job → expand the red step.
  • Every step logs its own stdout; the failing command's exit code is the cause.
  • Re-run a single failed job instead of the whole workflow.
  • Enable debug logs with repo secret ACTIONS_STEP_DEBUG=true.

Step naming & IDs

- name: Run tests        # log label
  id: tests              # referenceable handle
  run: npm test

- if: steps.tests.outcome == 'failure'
  run: echo "tests broke"

You need an id to read a step's outputs or outcome later.

Core actions

the four you'll use daily

The standard opening

steps:
  - uses: actions/checkout@v4          # pull your repo onto the runner

  - uses: actions/setup-node@v4        # install a specific Node
    with:
      node-version: 20
      cache: npm                       # built-in dependency caching

  - run: npm ci                        # exact versions from package-lock.json
  - run: npm test
RememberThe runner starts empty. Without checkout your code simply isn't there — this is the single most common "why is nothing working" moment.

Version pinning

@v4latest v4.x — moving tag, convenient
@v4.1.1exact release
@a1b2c3d…full commit SHA — immutable, safest
PracticePin third-party actions to a SHA. A moving tag can be repointed at malicious code.

npm ci vs npm install

npm ci installs exactly what package-lock.json says, wipes node_modules first, and errors if the lockfile is out of sync.

npm install can resolve to newer versions and mutate the lockfile.

In CI, always ciReproducible builds are the whole point.

Finding actions

GitHub Marketplace. Prefer:

  • actions/* — GitHub's own.
  • Verified creators (blue check).
  • Otherwise: read the source. Actions are open — the code you're granting runner access to is one click away.

Artifacts, outputs, cache

moving data between jobs

Which one do I want?

ArtifactFiles produced by a job — build output, test reports, binaries. Downloadable from the UI. Retained ~90 days.
OutputA short string — a filename, a URL, a version tag. Consumed by a later job via needs.
CacheReused files that can always be regenerated — node_modules, ~/.npm. A speed optimisation, never a delivery mechanism.
Don't confuse themNever cache build output to pass it downstream. Caches can be evicted at any time; artifacts are guaranteed.

Upload an artifact

- name: Upload dist
  uses: actions/upload-artifact@v4
  with:
    name: dist-files
    path: |
      dist
      package.json

Download it in the next job

deploy:
  needs: build
  runs-on: ubuntu-latest
  steps:
    - uses: actions/download-artifact@v4
      with:
        name: dist-files

It unzips into the working directory. Omit name to pull every artifact from the run.

Job outputs

jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      script-file: ${{ steps.publish.outputs.script-file }}
    steps:
      - name: Find JS bundle
        id: publish
        run: find dist/assets/*.js -type f -execdir \
             echo 'script-file={}' >> $GITHUB_OUTPUT ';'

  deploy:
    needs: build
    steps:
      - run: echo ${{ needs.build.outputs.script-file }}

Three hops: step writes to $GITHUB_OUTPUT → job re-exports it under outputs → consumer reads needs.<job>.outputs.<key>.

Deprecated::set-output is gone. Append key=value to $GITHUB_OUTPUT.

Caching dependencies

- name: Cache node modules
  uses: actions/cache@v4
  with:
    path: ~/.npm
    key: deps-node-${{ hashFiles('**/package-lock.json') }}
    restore-keys: deps-node-

The key is a fingerprint. Lockfile changes → new hash → cache miss → fresh install → new cache stored. That's automatic invalidation.

Skip install on a cache hit

- uses: actions/cache@v4
  id: cache
  with:
    path: node_modules
    key: deps-${{ hashFiles('**/package-lock.json') }}

- if: steps.cache.outputs.cache-hit != 'true'
  run: npm ci
Notecache-hit is the string 'true', not a boolean. Compare against the quoted string.

Env vars, secrets, environments

configuration & credentials

Three levels of env

env:                       # all jobs
  MONGODB_DB_NAME: gha-demo

jobs:
  test:
    env:                   # this job only
      PORT: 8080
    steps:
      - run: npm test
        env:               # this step only
          LOG_LEVEL: debug

Innermost wins. Read in YAML as ${{ env.PORT }}, in your code as process.env.PORT.

Useful default env vars

GITHUB_WORKSPACEcheckout path
GITHUB_SHAcommit hash
GITHUB_REFfull ref
GITHUB_RUN_NUMBERincrementing run counter
GITHUB_OUTPUTfile to append step outputs to
GITHUB_ENVfile to export vars to later steps
RUNNER_OSLinux / Windows / macOS
# set a var for all following steps
- run: echo "VERSION=1.2.3" >> $GITHUB_ENV

Secrets

Settings → Secrets and variables → Actions. Encrypted, write-only — you can never read one back in the UI.

env:
  MONGODB_PASSWORD: ${{ secrets.MONGODB_PASSWORD }}

Scopes: repository, environment, organization.

Leak riskValues are masked as *** in logs, but only if printed verbatim. Base64-encode or split a secret and the mask fails.

Environments

jobs:
  deploy:
    environment: production
    runs-on: ubuntu-latest

An environment gives a job its own secrets plus protection rules:

  • Required reviewers — job pauses until someone approves.
  • Wait timer — forced delay before it proceeds.
  • Deployment branches — only main may deploy here.
Why it mattersSame workflow, different credentials and gates per stage — testing / staging / production.

Secrets vs variables

secrets.Xencrypted, masked, unreadable after saving — API keys, passwords
vars.Xplaintext, viewable, editable — region names, bucket names, feature flags

Don't put a bucket name in secrets. Don't put a password in vars.

Conditional execution

if · status functions · continue-on-error

Default behaviour

When a step fails, every following step in that job is skipped and the job is marked failed. Which is exactly why an "upload the test report" step never runs when the tests fail — the thing you most want.

FixAdd if: failure() to that step.

Status check functions

success()implicit default — all previous steps passed
failure()something before this failed
always()run no matter what, including on cancel
cancelled()the run was cancelled
- name: Upload test report
  if: failure() && steps.run-tests.outcome == 'failure'
  uses: actions/upload-artifact@v4
  with: { name: test-report, path: test.json }
CriticalThe moment you write any if:, the implicit success() disappears. if: steps.x.outcome == 'failure' alone will never fire — you must pair it with failure().

outcome vs conclusion

outcomethe raw result, before continue-on-error is applied
conclusionthe result after it — a tolerated failure reads as success

To ask "did this actually fail?", use outcome.

continue-on-error

- name: Run tests
  id: run-tests
  continue-on-error: true
  run: npm test

The step may fail; the job carries on and stays green.

ifdecides whether the step runs at all
continue-on-errorlets a step that did run and fail be ignored

Conditional jobs

report:
  needs: [lint, deploy]
  if: failure()
  runs-on: ubuntu-latest
  steps:
    - run: echo "Something upstream broke"

Same field, job level. Without needs, failure() has nothing to observe — the pairing is what makes a failure-reporting job work.

Branch guard

deploy:
  if: github.ref == 'refs/heads/main'

# or on the event
  if: github.event_name == 'push'

# or skip drafts
  if: !github.event.pull_request.draft

Matrix & reusable workflows

scale and DRY

Matrix strategy

build:
  strategy:
    matrix:
      node-version: [18, 20, 22]
      os: [ubuntu-latest, windows-latest]
  runs-on: ${{ matrix.os }}
  steps:
    - uses: actions/setup-node@v4
      with:
        node-version: ${{ matrix.node-version }}

3 × 2 = 6 parallel jobs from one definition.

include & exclude

  matrix:
    node-version: [18, 20]
    os: [ubuntu-latest, windows-latest]
    include:
      - node-version: 22          # extra combo
        os: ubuntu-latest
    exclude:
      - node-version: 18          # drop this one
        os: windows-latest

fail-fast

  strategy:
    fail-fast: false       # default is true
    max-parallel: 2
    matrix: { … }

Default true cancels every sibling as soon as one combination fails. Set false when you want the full compatibility picture.

Reusable workflow — the callee

# .github/workflows/deploy.yml
on:
  workflow_call:
    inputs:
      artifact-name:
        required: false
        default: dist
        type: string
    secrets:
      api-key:
        required: true
    outputs:
      result:
        value: ${{ jobs.deploy.outputs.outcome }}

jobs:
  deploy:
    outputs:
      outcome: ${{ steps.d.outputs.result }}
    runs-on: ubuntu-latest
    steps:
      - run: echo ${{ inputs.artifact-name }}
      - run: echo ${{ secrets.api-key }}

Reusable workflow — the caller

jobs:
  deploy:
    needs: build
    uses: ./.github/workflows/deploy.yml
    with:
      artifact-name: dist-files
    secrets:
      api-key: ${{ secrets.API_KEY }}

  print:
    needs: deploy
    runs-on: ubuntu-latest
    steps:
      - run: echo ${{ needs.deploy.outputs.result }}
Noteuses sits at job level here — a reusable workflow replaces the whole job, so no runs-on and no steps beside it. Shortcut for passing everything: secrets: inherit.

Reusable workflow vs composite action

Reusable wfreplaces one or more jobs; can define its own runners & multiple jobs
Composite actionreplaces a group of steps inside someone else's job

Bundling "checkout + setup + install"? Composite action. Bundling "the entire deploy stage"? Reusable workflow.

Containers & services

controlling the environment

Why containers

A container packages your code plus its environment, so the runner's pre-installed versions stop mattering. Same image locally, in CI, in production.

Two distinct uses: run the job itself in a container, or run side services (a database) next to it.

Run a job in a container

test:
  runs-on: ubuntu-latest     # still need a host
  container:
    image: node:20-bullseye
    env:
      NODE_ENV: test
    ports: [8080]
    credentials:            # private registries
      username: ${{ secrets.REG_USER }}
      password: ${{ secrets.REG_PAT }}
  steps:
    - uses: actions/checkout@v4
    - run: npm ci && npm test

All run steps execute inside the image. actions/* still work.

Service containers

test:
  runs-on: ubuntu-latest
  services:
    mongodb:
      image: mongo
      ports: ['27017:27017']
      env:
        MONGO_INITDB_ROOT_USERNAME: root
        MONGO_INITDB_ROOT_PASSWORD: example

A throwaway database that lives for the job and shuts down with it. No shared test DB, no cleanup, no cross-contamination between runs.

How to reach the service

Job on the runnerconnect to localhost:27017 — needs the ports mapping
Job in a containerconnect to mongodb:27017 — the service label is the hostname, and no port mapping is needed
The classic bugJob runs in a container, code still says localhost. Both are on a Docker network now — use the label.

Custom actions

composite · JavaScript · Docker

Pick a type

CompositeBundle existing steps. Pure YAML, no code. Start here.
JavaScriptReal logic, fastest to start, runs directly on the runner via Node.
DockerAny language, full environment control. Slower — the image builds on every run. Linux runners only.

All three live in a folder containing action.yml.

Composite action

# .github/actions/cached-deps/action.yml
name: Get & cache dependencies
description: Install npm deps with caching
inputs:
  caching:
    description: Use cache?
    required: false
    default: 'true'
outputs:
  used-cache:
    description: Whether cache was used
    value: ${{ steps.install.outputs.cache }}
runs:
  using: composite
  steps:
    - uses: actions/cache@v4
      if: inputs.caching == 'true'
      with:
        path: node_modules
        key: deps-${{ hashFiles('**/package-lock.json') }}
    - name: Install
      id: install
      run: npm ci
      shell: bash            # REQUIRED in composite
Two trapsEvery run step must declare shell:, and inputs are read as inputs.x — never env.x.

Using a local action

steps:
  - uses: actions/checkout@v4     # must come FIRST
  - name: Install deps
    id: deps
    uses: ./.github/actions/cached-deps
    with:
      caching: 'false'
  - run: echo ${{ steps.deps.outputs.used-cache }}
Order mattersA local action is a file in your repo. Without checkout first, the path doesn't exist yet.

JavaScript action

# action.yml
runs:
  using: node20
  main: main.js
  # optional: pre / post scripts
// main.js
const core = require('@actions/core');
const exec = require('@actions/exec');

function run() {
  const bucket = core.getInput('bucket', { required: true });
  core.notice(`Deploying to ${bucket}`);
  await exec.exec(`aws s3 sync ./dist s3://${bucket}`);
  core.setOutput('website-url', `http://${bucket}.s3-website...`);
}
run();

Toolkit: @actions/core (inputs, outputs, logging, failure), @actions/github (context & API), @actions/exec (shell).

Ship the depsThe runner won't npm install for you. Commit node_modules, or bundle with @vercel/ncc.

Docker action

runs:
  using: docker
  image: Dockerfile       # or docker://alpine:3.19

Inputs arrive as env vars, upper-cased and prefixed:

# input `bucket` becomes:
os.environ['INPUT_BUCKET']

Outputs are written the same way as everywhere else — append to $GITHUB_OUTPUT.

Sharing an action

  • Same repo — ./.github/actions/name
  • Own repo — owner/repo@v1, with action.yml at the root
  • Marketplace — tag a release and publish from the repo page

Publishing needs a root-level action.yml, a unique name, and a README.

Security & permissions

the part that gets people fired

Script injection

Anything a user can type — issue titles, PR bodies, branch names — is attacker-controlled. Interpolating it into a shell command runs it.

# VULNERABLE — an issue titled  a"; rm -rf /; echo "  executes
- run: echo "Title: ${{ github.event.issue.title }}"

# SAFE — value passes through the env, never through the shell parser
- run: echo "Title: $TITLE"
  env:
    TITLE: ${{ github.event.issue.title }}
RuleNever put ${{ }} containing user input directly inside a run: block. Bind it to an env var, or pass it to an action via with.

GITHUB_TOKEN

Auto-generated per run, auto-expires when the run ends. Use it to call the GitHub API — no PAT needed.

- run: gh issue comment 1 --body "ok"
  env:
    GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}

Settings → Actions → Workflow permissions sets the repo-wide default. Choose read-only and grant more per workflow.

permissions

# workflow level — applies to every job
permissions:
  contents: read
  issues: write

jobs:
  deploy:
    permissions:          # job level overrides
      id-token: write
      contents: read
All-or-nothingDeclaring a permissions block sets every unlisted scope to none. List everything the job needs. permissions: {} drops all of them.

OpenID Connect

Instead of storing long-lived AWS keys as secrets, the runner requests a short-lived token that AWS trusts.

permissions:
  id-token: write
  contents: read

steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123:role/gh-deploy
      aws-region: us-east-1

Cloud side: register GitHub as an OIDC identity provider, create a role with a trust policy scoped to your repo. Nothing to rotate, nothing to leak.

Third-party actions

  • Prefer actions/* and verified creators.
  • Pin to a full commit SHA, not a tag.
  • Read the source before granting it your runner.
  • Restrict which actions may run: Settings → Actions → Allow select actions.
ThreatAn action runs arbitrary code with access to your workspace, env, and token. A compromised tag is a supply-chain breach.

Remaining settings

  • Require approval for all outside collaborators, not just first-timers.
  • Turn off "Allow Actions to create and approve pull requests" unless you need it.
  • Protect main: require PR review + passing checks.
  • Gate production behind an environment with required reviewers.

Last-minute recall

the things that break builds

Ten reflexes

  • Workflows only load from .github/workflows/ on the default branch for scheduled and dispatch events.
  • No checkout = no code. Always step one.
  • Jobs are parallel until you add needs.
  • Nothing on disk survives a job boundary.
  • Writing any if: removes the implicit success().
  • cache-hit is the string 'true'.
  • Composite run steps must set shell:.
  • Declaring permissions zeroes out everything you didn't list.
  • Never interpolate user input into run:.
  • Fork PRs get no secrets and a read-only token — by design.

YAML traps

  • Indentation is spaces only. A tab is a parse error.
  • on parses as boolean true in YAML 1.1 — GitHub handles it, other linters may not.
  • Quote anything starting with *, &, {, % or @.
  • | keeps newlines, > folds them into spaces.
  • 'true' in a with: block is a string; true is a boolean. Actions usually want the string.
